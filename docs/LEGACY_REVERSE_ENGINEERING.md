# 旧版逆向记录

本文记录需要反复引用的 1.9.13 旧实现证据。它不是实现计划；实现计划仍以 `BUILT_IN_ROADMAP.md` 和 `BUILT_IN_ACTION_TRACKER.md` 为准。

## ActivatorSpringBoard 解混淆记录

当前参考输入是 `references/latest/Library/Activator/ActivatorSpringBoard.bundle/ActivatorSpringBoard`。该 Mach-O 是 universal binary，包含 armv6、arm64、arm64e slice；本次分析使用 arm64 slice。已解混淆二进制和 IDA 数据库保存在 `references/latest/analysis/ActivatorSpringBoard/`，该目录只作为本地参考快照复用，不提交到仓库。

`LC_ENCRYPTION_INFO_64` 中的 `cryptid` 为 `0`，因此这里处理的不是 FairPlay 加密，而是 Activator 自己对字符串和 ObjC metadata 做的混淆。未处理的二进制中，`__objc_classname`、`__objc_methname`、`__objc_methtype` 和 `__cstring` 的关键内容不可直接用 strings / IDA 识别。

可复现的处理步骤如下：

```sh
lipo -thin arm64 references/latest/Library/Activator/ActivatorSpringBoard.bundle/ActivatorSpringBoard -output references/latest/analysis/ActivatorSpringBoard/ActivatorSpringBoard.arm64
otool -l references/latest/analysis/ActivatorSpringBoard/ActivatorSpringBoard.arm64 | rg -C 3 'LC_ENCRYPTION|crypt'
```

对比已解混淆产物 `references/latest/analysis/ActivatorSpringBoard/ActivatorSpringBoard.arm64.decrypted` 可见两段连续区域发生变化：`0x3f3e1..0x47ab2` 覆盖 ObjC class / method / type metadata，`0x49ab1..0x50719` 覆盖 `__cstring`。这两段使用相同的滚动 XOR 规则，分别以 `0x72` 作为初始 `previous` 值：

```c
uint8_t previous = 0x72;
for (uint64_t offset = rangeStart; offset < rangeEnd; offset++) {
    uint8_t plain = data[offset] ^ previous;
    data[offset] = plain;
    previous = plain;
}
```

该规则可以由 `0x3f3e1` 起始处验证：原始字节 `0x33` 与 seed `0x72` 异或得到 `A`，下一字节 `0x22` 与上一明文字节 `A` 异或得到 `c`，解出的开头为 `ActivatorSlideGestureRecognizer`。明文字节为 NUL 时，下一密文字节等于上一明文字节，这也符合滚动 previous-plaintext XOR。

解混淆后再用 IDA 分析 `references/latest/analysis/ActivatorSpringBoard/ActivatorSpringBoard.arm64.decrypted.i64`。后续引用旧实现时，应说明证据来自这个解混淆后的本地分析产物，避免把原始混淆二进制中的缺失字符串误判为旧版没有实现。

## Status bar gestures

旧 master 中状态栏触摸分为两条路径：SpringBoard 端 `Events.x` hook `SBStatusBar`，只能派发通用 `libactivator.statusbar.tap.single`、`tap.double`、`hold`、`swipe.left`、`swipe.right`、`swipe.down`；UIKit everywhere 注入端 `EverywhereHooks.x` hook `UIStatusBar`，按触摸起点的 `x < width * 0.25`、`width * 0.25 <= x < width * 0.75`、`x >= width * 0.75` 分别派发 left、base、right 的 tap/hold/double-tap 事件。旧阈值来自 `references/master/Constants.h`：hold delay `0.5` 秒，single tap delay `0.33` 秒，horizontal swipe threshold `50.0pt`，vertical swipe threshold `10.0pt`；移动方向使用 `deltaX^2 > deltaY^2` 决定横向优先还是纵向优先。

旧 master 的 `EverywhereHooks.x` 在 `touchesBegan:` 中启动 hold timer 并记录起点；`touchesMoved:` 会取消 hold/tap timer，达到横向阈值时派发 `statusbar.swipe.right/left`，达到向下纵向阈值时在旧 CoreFoundation 版本下派发 `statusbar.swipe.down`；`touchesEnded:` 中 `tapCount == 2` 立即派发 double tap，否则延迟 `0.33` 秒派发 single tap。该 hook 在 single tap fallback 中通过 `passThroughStatusBar` 重新调用一次 `touchesBegan:` 并继续 `%orig`，说明旧实现也尽量保留系统状态栏默认行为，而不是在事件识别阶段直接吞掉触摸。

1.9.13 的解混淆 `ActivatorSpringBoard` 中仍可见 `ActivatorSlideGestureRecognizer`、`ActivatorSystemGestureRecognizer`、`UIStatusBarWindow`、`UIStatusBar`、`SBOffscreenSwipeGestureRecognizer`、`libactivator.statusbar.swipe.down` 和 `libactivator.statusbar.` 前缀。IDA 中 `UIStatusBar initWithFrame:showForegroundView:` 的 replacement 会在原始初始化后创建并 `addGestureRecognizer:` 一个 recognizer；`UIStatusBarWindow initWithFrame:` 在存在 `SBOffscreenSwipeGestureRecognizer` 时也会向 window 加 recognizer。`libactivator.statusbar.swipe.down` 的 xref 落在 slide/edge gesture 计算逻辑，符合 public header 中 “Now a slide in gesture on iOS5.0+; extern and name kept for backwards compatibility” 的注释。因此现代实现应把 `statusbar.swipe.down` 当作历史兼容事件保留，但完整 top slide / edge gesture family 应单独实现。

1.9.13 中 screen-side swipe public constants 是旧 API 名称保留，但实际字符串已更名到 `drag-along` event namespace，而不是新增一套 `screen.*.swipe.*` 事件。证据来自 `references/latest/package/usr/lib/libactivator.dylib` arm64 slice：导出符号 `_LAEventScreenBottomSwipeLeft` 到 `_LAEventScreenRightSwipeUp` 仍存在，`__TEXT,__cstring` 中不存在 `libactivator.screen.*.swipe.*` 字符串，只存在 `libactivator.drag-along.*`；`__DATA_CONST,__const` 中这些 symbol 依次指向 `libactivator.drag-along.screen-bottom.right-to-left`、`libactivator.drag-along.screen-bottom.left-to-right`、`libactivator.drag-along.screen-left.top-to-bottom`、`libactivator.drag-along.screen-left.bottom-to-top`、`libactivator.drag-along.screen-right.top-to-bottom` 和 `libactivator.drag-along.screen-right.bottom-to-top`。因此当前项目的 `LAEventScreen*Swipe*` 常量值必须以 1.9.13 为准映射到 `drag-along` 名称，不能保留旧推测的 `libactivator.screen.*.swipe.*`。

1.9.13 的解混淆 `ActivatorSpringBoard` 中，`ActivatorSlideGestureRecognizer` 与 `ActivatorSystemGestureRecognizer` 共享一组 slide / drag helper。IDA 中 `ActivatorSlideGestureRecognizer touchesBegan:` 进入 `sub_4FFC`，该函数记录起点并读取旧偏好倍率，默认得到 `13.0pt` edge band；slide-in 内移触发 rect 继续使用 `13 + 50 = 63pt`。同一函数只为单指起点挂载 `drag-along` candidate：bottom、left、right 三条边，不存在 top drag-along；bottom 起点判断带 `2pt` fudge，即默认约 `height - 15pt` 内。`sub_4C1C` 在 moved path 先判断 slide-in，未触发时再判断 drag-along：bottom 横向 delta 需超过 `30pt` 且 y 保持在起点约 `5pt` 内；left/right 纵向 delta 需超过 `30pt` 且 x 保持在起点约 `5pt` 内。`ActivatorSlideGestureRecognizer touchesEnded:` 与 `ActivatorSystemGestureRecognizer touchesEnded:` 都会进入 `sub_4A0C` 处理 `drag-off`：起点必须先落在 `(25,25,width-50,height-50)` 内部区域；结束点进入 left/right/top/bottom 的 `20pt` 边缘区才派发 `libactivator.drag-off.left/right/top/bottom`，同时用另一轴的 `20pt` / `height-or-width - 50pt` 范围排除角落。`touchesCancelled:` 只清理状态，不走 `drag-off` 分类。

需要注意，旧实现的这些阈值是在 recognizer 自己的 view 坐标里计算：旧 master 中 `ActivatorSlideGestureRecognizer` 使用 `[touch locationInView:self.view]`，并按 `SpringBoard activeInterfaceOrientation` 对 `UIScreen.mainScreen.bounds.size` 做横竖屏归一化；1.9.13 的解混淆实现也保持 recognizer/view helper 结构。当前项目的 runtime 数据源是 `_UISystemGestureWindow sendEvent:` 中 `[touch locationInView:window]` 与 `window.bounds`，该 window 坐标与旧 recognizer view 坐标不完全等价；但 drag-along / drag-off 当前仍选择直接对齐 1.9.13 阈值，后续只有在真机验收明确证明需要时再调整。

当前项目不使用旧 `com.apple.UIKit` filter 注入用户 App 进程。现代 iOS 目标点位改为 SpringBoard 进程内多个 `UIStatusBar_Modern` 实例：主屏幕、锁屏和前台 App 界面各自可能有独立实例。实现时应在 SpringBoard tweak 内 hook `UIStatusBar_Modern` 的 touch 方法，并让每个 status bar view 实例拥有独立识别 session，避免旧 master 的全局状态在多实例现代状态栏下串扰。

## Force touch events

1.9.13 的解混淆 `ActivatorSpringBoard` 中，force touch 由 `ActivatorSystemGestureRecognizer` 承载。相关字符串使用固定 XOR `0x1e` 混淆，解出后可见六个 runtime event name：`libactivator.force-touch.statusbar`、`libactivator.force-touch.screen-left`、`libactivator.force-touch.screen-right`、`libactivator.force-touch.screen-bottom-left`、`libactivator.force-touch.screen-bottom`、`libactivator.force-touch.screen-bottom-right`。旧实现从 `UITouch` 读取 `force`，而不是直接读取 HID digitizer pressure；当前 Frida probe 额外确认底层 HID pressure 与 `UITouch.force` 近似线性对应，但实现应以 `UITouch.force` 为语义来源。

旧实现的区域划分来自同一 recognizer 的 region helper：`y < 38pt` 为 statusbar；`y >= height - 38pt` 为 bottom 区域，其中 `x < width * 0.25` 是 bottom-left，`x < width * 0.75` 是 bottom，其余是 bottom-right；非 bottom/statusbar 时，`x < 14pt` 是 left，`x > width - 14pt` 是 right。force 阈值约为 `5.0`；旧反编译比较接近 `force > 5.0`，当前实现使用 `force >= 5.0` 作为可测试阈值，避免浮点边界让 stable 测试依赖不可表达的“略大于”。旧实现路径没有显示出要拦截原始系统触摸的行为，当前阶段也继续调用原始 `_UISystemGestureWindow sendEvent:`。

## `libactivator.audio.launch-playing-app`

1.9.13 中该 listener name 对应 `_LANowPlayingApplicationListener`，关键方法是 `-applicationForListenerName:`。解混淆后的引用可以看到 `_LANowPlayingApplicationListener`、`nowPlayingApplication`、`SBMediaController`、`SBApplicationController`、`com.apple.Music` 和 `libactivator.audio.launch-playing-app`。

旧实现语义是先取 `SBMediaController.sharedInstance`，如果它能响应并返回 `nowPlayingApplication`，则使用这个 now-playing application。若没有可用 now-playing application，则 fallback 到 `SBApplicationController.sharedInstance`，按 CoreFoundation 版本选择 `applicationWithDisplayIdentifier:` 或 `applicationWithBundleIdentifier:`，传入固定 bundle id `com.apple.Music`。

现代实现不能把这个 fallback 直接当成目标语义照搬。旧 fallback 是“无法确认 now-playing app 时打开 Music”的兼容行为，但当前项目的设计边界是不使用静态 Music fallback 伪装 now-playing identity。真机 Frida 验证显示，现代 iOS 上 `SBMediaController nowPlayingApplication` 可以返回 `nil`，但 `MRMediaRemoteGetNowPlayingApplicationDisplayID` 能回调真实 display identifier，例如 `com.apple.Music`；`MRMediaRemoteGetNowPlayingApplicationPID` 也能返回 now-playing PID，并可用 `SBSCopyDisplayIdentifierForProcessID` 转换为 display identifier。因此当前实现不保留 `SBMediaController` 路径，改用 MediaRemote display id 优先、PID + SpringBoardServices fallback 的 identity provider，再交给 SpringBoard 私有打开路径；如果没有 now-playing identity，listener 仍消费事件并记录诊断，但不打开静态 fallback。

## `libactivator.ipod.music-controls`

1.9.13 中 `musicControls` 是 `_LASimpleListener` 上的旧 selector。解混淆后的实现引用了 `SBNowPlayingAlertItem`、`SBAlertItemsController` 和 `SBMediaController`。

旧实现大意是：如果 `SBNowPlayingAlertItem` 已经显示，则通过 `SBAlertItemsController` 关闭；否则在可显示 now-playing UI 的条件下创建并激活一个 `SBNowPlayingAlertItem`。若该 UI 路径不可用，则退回到打开 now-playing application / Music fallback 的路径。

这个语义依赖旧 SpringBoard 的 now-playing alert modal。现代 iOS 已没有对应的 `SBNowPlayingAlertItem` 用户体验，当前采用用户可见的等价入口：必要时先点亮屏幕，再打开 Control Center 并切换 Now Playing 模块展开状态。实现不只打开 Control Center；SpringBoard tweak hook `CCUIModuleCollectionViewController -viewDidLoad` 缓存实例，并在 `-viewWillAppear:` 时对模块 ID `com.apple.mediaremote.controlcenter.nowplaying` 使用 `isModuleExpandedForIdentifier:` 判断当前状态，已展开则 `dismissExpandedModuleAnimated:completion:` 收起，未展开则 `expandModuleWithIdentifier:` 展开。`libactivator.system.show-now-playing-bar` 使用同一现代等价实现。

## Lock screen / switcher / power actions

阶段 3 收口的锁屏、Switcher 和电源类 actions 优先采用 `XXTouchLite/device/DeviceConfigurator.mm` 非 `THEBOOTSTRAP` 分支作为现代 iOS 参考实现；1.9.13 的解混淆 `ActivatorSpringBoard` 只用于确认 Activator selector、动作语义和参考实现未覆盖的 UI 动作。`libactivator.lockscreen.show` 使用 `SBLockScreenManager.sharedInstance remoteLock:YES`，不执行背光 fade out。`libactivator.lockscreen.dismiss` 如果屏幕未亮，先通过 `LATRuntimeStateSource wakeScreenForReason:completion:` 走项目内 Power HID 唤醒和 screen-on state 回调，再调用 `SBLockScreenManager attemptUnlockWithPasscode:@"" finishUIUnlock:YES completion:nil`，fallback 到 `attemptUnlockWithPasscode:@""`；该路径只支持无密码设备或系统允许空 passcode 解锁的状态，不复刻 1.9.13 的 `SBCoverSheetPresentationManager unlockUIFromSource:withOptions:`，也不再直接依赖 `SBBacklightController turnOnScreenFullyWithBacklightSource:`。

`libactivator.system.respring` 使用 `SBSRelaunchAction` 和 `FBSSystemService sendActions:withResult:`，不加入 batch kill fallback。`libactivator.system.hard-respring` 使用同一路径并带上 `SBSRelaunchActionOptionsRestartRenderServer`，对应 `DeviceConfigurator _respringCompletely:YES` 的现代参考语义。`libactivator.system.soft-reboot` 曾参考 Dopamine `jbctl reboot_userspace` 的 `reboot3(RB2_USERREBOOT)` 路径，但该路径在 SpringBoard 进程内无法执行；当前从 staged resource 和 runtime allowlist 移除，后续需要非 SpringBoard helper 或合适 privileged execution path。`libactivator.system.powerdown` / `reboot` 使用 `SpringBoard.restartManager shutdownForReason:nil` / `rebootForReason:nil`。

`AXSpringBoardServer` 暴露的 Accessibility SpringBoard server SPI 已用于补齐部分系统 UI actions。旧 master 与 1.9.13 均显示多个 `activate-*` action 不是单向 activate：`libactivator.system.activate-control-center` 先查 `isControlCenterVisible`，再通过 `showControlCenter:` 在打开和关闭之间切换；`activate-notification-center` 先查 `isNotificationCenterVisible`，已打开时优先调用 `hideNotificationCenter`，否则调用 `showNotificationCenter:` / `showNotificationCenter`；`activate-switcher` 先查 `isAppSwitcherVisible`，已打开时调用 `dismissAppSwitcher`，否则调用 `openAppSwitcher`，原 `SBSwitcherController` / `SBMainSwitcherViewController` 路径只作为 fallback；`activate-reachability` 按旧实现语义保持 toggle，当前主队列调用 `AXSpringBoardServerHelper isReachabilityActive` 后再 `setReachabilityActive:` 为相反状态。四个 rotation actions 调用 `setOrientation:`，orientation 值使用 UIKit `UIInterfaceOrientation` 常量。旧 master 的 `libactivator.system.voice-control` 依赖 `SBVoiceControlAlert` 且在 alert 已存在时会 cancel；现代实现改为切换系统 Voice Control 功能。设备上 AccessibilitySettings 的 `-[CACSettingsController setCommandAndControlEnabled:specifier:]` 只调用 `_AXSCommandAndControlSetEnabled([value boolValue])`，`-[CACSettingsController commandAndControlEnabled:]` 只包装 `_AXSCommandAndControlEnabled()`，因此当前 SpringBoard runtime 通过 `/usr/lib/libAccessibility.dylib` 动态解析这两个符号后执行 toggle。`libactivator.system.wallet` 调用 `armApplePay`。

`AccessibilityPhysicalInteraction.framework` 中的 `AXPISystemActionHelper` 需要先通过 `NSBundle` 加载 `/System/Library/PrivateFrameworks/AccessibilityPhysicalInteraction.framework`，再用 `NSClassFromString(@"AXPISystemActionHelper") sharedInstance` 获取实例。`libactivator.audio.mute-ringer` / `unmute-ringer` / `toggle-ringer-mute` 首选该 helper 的 `toggleRingerSwitch:` 和 `isRingerSwitchOn`，不影响 `reset-ringer-state` 的硬件状态同步语义；原 `SBRingerControl setRingerMuted:` 路径保留为 fallback。旧 master 的 `libactivator.system.virtual-assistant` 是 toggle：Siri 已可见时 dismiss，不可见时 activate；当前实现用 `AXSpringBoardServer isSiriVisible` / `dismissSiri` 处理关闭，用 `AXPISystemActionHelper activateSiri` 处理打开，资源 selector 仍对齐当前 staged metadata 的 `activateSiri`。

1.9.13 中 `libactivator.system.haptic.flick` / `tap` / `quirk` 共用 selector `tapticWithActivator:event:listenerName:`，从 listener metadata 读取 `tapticType`：`flick=0`、`tap=1`、`quirk=2`。解混淆实现显示 iOS 13 路径优先使用 UIKit public haptics：`flick` 创建 `UIImpactFeedbackGenerator` 并以 `UIImpactFeedbackStyleHeavy` 触发 `impactOccurred`，`tap` 使用 `UIImpactFeedbackStyleLight`，`quirk` 创建 `UINotificationFeedbackGenerator` 并以 `UINotificationFeedbackTypeSuccess` 触发 `notificationOccurred:`。旧实现还保留 `_tapticEngine` fallback，但当前现代 iOS 实现不复刻该旧 fallback。

1.9.13 中 `libactivator.system.power-menu` 的 selector `powerDownView` 语义是显示电源选项。首轮 `SBPowerDownController _instanceIfExists presentPowerDownTransientOverlay` 和 SpringBoard application `lockButtonWasHeld` / `showPowerDownAlert` fallback 路径真机验证无效；后续 trace 确认现代入口是 `SBMainWorkspace.sharedInstance[IfExists] presentPowerDownTransientOverlay`，用户取消时系统会走 `dismissPowerDownTransientOverlayWithCompletion:`。`libactivator.system.activate-switcher` 的 iOS 16+ 入口为 `SBMainSwitcherControllerCoordinator._activeDisplaySwitcherController` 返回的 `SBSwitcherController toggleMainSwitcherNoninteractivelyWithSource:0x14 animated:YES`，iOS 18+ 优先 `toggleMainSwitcherWithSource:animated:`；iOS 15+ fallback 使用已验证的 `SBMainSwitcherViewController sharedInstance activateMainSwitcherNoninteractivelyWithSource:1 animated:YES`。`libactivator.system.edit-screenshot` 的 selector `editScreenshot` 语义是立即截图并进入编辑，优先 `_takeScreenshotAndEdit:`，fallback `takeScreenshotAndEdit:`，再 fallback 普通 `takeScreenshot`。`libactivator.system.safemode` 在 1.9.13 中实现为延迟向 `UIApp` 发送 `safeModeFromActivator`；项目 owner 已明确接受这是主动制造 SpringBoard exception 以触发 loader Safe Mode，不需要额外 probe。`libactivator.system.clear-switcher` 的首轮 app layout 删除路径真机验证无效，当前不注册 runtime listener。`libactivator.system.lock-and-wipe-credentials` 的 1.9.13 options key 已解出为 `SBUILockOptionsUseScreenOffModeKey`、`SBUILockOptionsForceBioLockoutKey` 和 `SBUILockOptionsForceLockKey`，语义是锁屏并强制 biometric lockout，不是删除 passcode 或清除系统凭据。iOS 16.7 dyld shared cache 中 `SBPowerDownViewController -handleLockButtonPress` 会直接调用 `SBUIBiometricResource.sharedInstance _forceBioLockout`；`SBLockScreenManager -lockUIFromSource:withOptions:completion:` 在 `SBUILockOptionsForceBioLockoutKey` 为真时同样调用 `_forceBioLockout` 并发出 `com.apple.springboard.lock-with-force-biolockout` 通知。当前实现因此不再使用首轮验证无效的 `SBCoverSheetPresentationManager lockUIFromSource:withOptions:`，而是通过 `SBLockScreenManager lockUIFromSource:withOptions:completion:` 传入上述三项 options。

## Compose actions

`libactivator.mail.compose-message`、`libactivator.sms.compose-message`、`libactivator.notes.compose-note` 分别使用 selector `composeMail`、`composeText`、`composeNote`。1.9.13 中 Mail 与 SMS 通过 action object 呈现 `MFMailComposeViewController` / `MFMessageComposeViewController`，Notes 直接通过 `SLComposeViewController composeViewControllerForServiceType:@"com.apple.mobilenotes.SharingExtension"` 呈现系统 Notes sharing extension。三者都使用临时 `UIWindow` presenter；当 compose UI 已经存在时，再次触发会关闭当前 UI。

当前实现将这三项收口到独立 `LATComposeActionListener` family。Mail/SMS 继续运行时加载 `MessageUI.framework`；Notes 旧 `Social.framework` / sharing extension 路径在现代 iOS 验证无效，不再保留 fallback。`/Users/82flex/Desktop/SystemQuickNoteModule` 的 IDA 结果显示 Control Center Quick Note 的日志 `About to open System Paper from the Control Center` 位于 `-[ICSystemPaperControlCenterModule handleTapWithTouchType:]`，核心现代入口是 `-[ICSystemPaperControlCenterModule activateSystemPaper]`：iPad/Mac idiom 使用 `SBSSystemNotesPresentationConfiguration initWithSceneBundleIdentifier:@"com.apple.mobilenotes" userActivity:nil preferredPresentationMode:0` 和 `SBSSystemNotesPresentationHandle initWithConfiguration:` 后 `activate`；iPhone 在 `__os_feature_enabled_impl("PencilAndPaper", "QNOnPhone")` 通过时使用 `SBSRemoteAlertDefinition initWithServiceName:@"com.apple.SystemPaperViewService" viewControllerClassName:@"ViewController"`、`SBSRemoteAlertHandle newHandleWithDefinition:configurationContext:` 和 `activateWithContext:`。Stable tests 只验证 listener 注册、allowlist 与 selector metadata，不触发真实 compose UI。

## Phone actions

旧 master 的 `_LASimpleListener` 中包含 5 个 Phone tab selector：`showPhoneFavorites`、`showPhoneRecents`、`showPhoneContacts`、`showPhoneKeypad`、`showPhoneVoicemail`。这些动作没有 `url` metadata，但旧实现内部直接调用 SpringBoard `applicationOpenURL:publicURLsOnly:`；CoreFoundation 版本小于 675 时使用 `doubletap://com.apple.mobilephone?view=...`，675 及之后使用 `mobilephone-recents:favorites`、`mobilephone-recents:`、`mobilephone-recents:contacts`、`mobilephone-recents:keypad` 和 `vmshow:`。当前实现按真机验证结果使用 `mobilephone-favorites:`、`mobilephone-recents:`、`mobilephone-contacts:`，voicemail 继续使用 `vmshow:`；`phone.keypad` 恢复旧 `mobilephone-recents:keypad` URL，但现代 iOS 单靠 URL 不会切换拨号键盘，因此新增只注入 `com.apple.mobilephone` 的 companion tweak。MobilePhone 逆向显示 `PhoneTabBarController -handleURL:` 不处理 `mobilephone-recents:keypad`，实际 root 是 `MPRootViewController`，需通过 `-baseViewController` 取得 `PhoneTabBarController`。`PhoneTabBarController -switchToTab:` 的 IDA 结果显示 keypad 分支取 `keypadViewController`，但实现不硬编码 tab type；companion tweak 先取 `keypadViewController`，再通过 `tabTypeForViewController:` 反查当前系统实际 tab type 并调用 `switchToTab:`。打开路径通过 `LSApplicationWorkspace openSensitiveURL:withOptions:error:` 在非主队列提交。

## Camera actions

`libactivator.camera.invoke-shutter` 的旧语义是先尝试相机快门；失败时打开 `com.apple.camera` 并等待 `libactivator.camera.ready` 后重试。当前现代实现拆成 SpringBoard listener 与只注入 Camera 的 companion tweak：SpringBoard 端 `LATCameraActionListener` 先按事件 mode 或 runtime `isUILocked` 判断锁屏状态，锁屏状态优先走 CoverSheet camera，避免“Camera App 在锁屏底下”时被 foreground app 短路；非锁屏状态才判断当前前台是否为 `com.apple.camera` 并直接发送 Consumer page `VolumeDecrement` HID。锁屏 camera 复用 `LATLockScreenCameraLauncher`，但 `activateCameraViewAnimated:sendingActions:completion:` completion 不再视为可拍 ready；completion 或 `SBApplicationsRegisteredForVolumeButtonEventsChangedNotification` 到达后，仅在 CoverSheet camera visible 的前提下延后 0.6s 复核，且 SpringBoard `appsRegisteredForVolumeEvents.firstObject.bundleIdentifier == com.apple.camera` 时才发送 HID，否则继续等待直到 pending shutter timeout。普通 Camera app launch 用 `SBSLaunchApplicationWithIdentifierAndLaunchOptions` 并等待 Darwin notification `libactivator.camera.ready`，ready 到达后单次检查前台是否为 `com.apple.camera`。Camera 端通过 IDA 重新建库分析 `/Users/82flex/Desktop/dyld/com.apple.dyld_16.7/dyld_shared_cache_arm64` 中的 `/System/Library/PrivateFrameworks/CameraUI.framework/CameraUI`，确认 `CAMViewfinderViewController -_shouldEnableShutterButton` 只等价于 `_reasonsToDisableShutterButton == nil`，早于物理音量键接管；`UIApplication setWantsVolumeButtonEvents:YES` 也只说明 physical capture recognizer/notifier 已请求音量键事件，仍早于 viewfinder 控件状态更新。Frida attach 已运行 Camera 后触发 `libactivator.camera.invoke-shutter`，真实路径显示先进入 `CAMViewfinderViewController -_updateEnabledControlsWithReason:`，reason 为 `Physical capture button pressed`，随后 `_shouldEnableShutterButton` / `_reasonsToDisableShutterButton` / `CUCaptureController isCaptureAvailable` 均返回可拍状态，之后进入 `_handleShutterButtonPressed:`；同一 probe 未观察到 `captureController:didOutputCaptureAvailability:` 在前后台路径稳定重放。真机前后台日志显示恢复前台时先 `UIApplication setWantsVolumeButtonEvents:YES`，随后 `CAMViewfinderViewController _updateEnabledControlsWithReason:forceLog:` 报告 `Finished opening viewfinder` 且 active / wantsVolumeButtonEvents 均为 1；关闭路径则会释放 volume events 并出现 `Began closing viewfinder` / `Finished closing viewfinder` / `Capture Controller Interrupted`。因此 companion tweak hook `CAMViewfinderViewController -_updateEnabledControlsWithReason:forceLog:`，仅在该回调当场满足 Camera app active 且已请求 volume button events 时安排延迟 ready，0.6s 后复核条件仍成立才发送 `libactivator.camera.ready`；后台、关闭或释放 volume events 会取消待发送。SpringBoard 端 completion / ready 到达后条件不满足就丢弃 pending shutter，不在 timeout 后补发 HID。

`libactivator.system.previous-app` 是 1.9.13 新增动作，旧 bundled metadata 描述为 “Launch previously activated app”，当前 staged resource 以 selector `previousApp` 作为实现 gate。1.9.13 `ActivatorSpringBoard` 中它不是 `_LASimpleListener` selector，而是单独的 `_LAPreviousApplicationListener`；该类只覆写 `applicationForListenerName:`，IMP `sub_BC8C` 先检查上一 App 全局状态，存在时通过 `SBApplicationController sharedInstance applicationWithBundleIdentifier:`（旧系统 fallback 为 `applicationWithDisplayIdentifier:`）解析 App object，再复用 `_LAApplicationBaseListener` 的通用 `launchApplication:shortcutItem:forEvent:` 路径。当前现代实现不复刻旧全局变量，而是在 `LATRuntimeStateSource` 采集前台 App 时用 O(1) 缓存记录最近打开的 App 和前一个不同 App：当前处于 App 内时打开前一个 App，当前处于 SpringBoard/主屏幕时打开最近打开过的 App，并由 `LATSystemPreviousApplicationController` 通过统一 `LATApplicationLauncher` 打开该 identifier。

`_SBXXSetWantsVolumeButtonEvents` 位于 `/System/Library/PrivateFrameworks/SpringBoard.framework/SpringBoard`，由 `-[SpringBoard _initializeDeferredItems]` 通过 `setFunction:forSymbol:` 注册。调用链为 UIKit / CameraUI 端 `UIApplication setWantsVolumeButtonEvents:` -> SpringBoard.framework `__SBXXSetWantsVolumeButtonEvents`，后者用 audit token 解析 `SBRunningApplicationForAuditToken`，再异步调用 `_SBApp setAppRegisteredForVolumeEvents:isActive:`。`-[SpringBoard setAppRegisteredForVolumeEvents:isActive:]` 维护 `SpringBoard->_appsRegisteredForVolumeEvents`：先移除该 app，active 时插入到 index 0，然后发送 `SBApplicationsRegisteredForVolumeButtonEventsChangedNotification`。SpringBoard 真实音量键路径中，`SBPressPrecedenceArbiter _currentButtonPriority` 读取 `appsRegisteredForVolumeEvents.firstObject` 参与按键优先级判定；`SBVolumeHardwareButtonActions _sendVolumeButtonDownToLegacyRegisteredClientsForIncrease:` 同样读取 firstObject，并且在 `SBWorkspaceHasApplicationSceneInLockedOrUnlockedEnvironmentLayoutStateMatchingApplication(app)` 成立时通过 `SBSendFakeButtonPressEventToApplication(bundleIdentifier, pid, 102/103, 1)` 转发 legacy volume down/up。当前 `LATCameraActionListener` 在发送 synthetic `VolumeDecrement` HID 前只使用可直接访问的 SpringBoard getter `appsRegisteredForVolumeEvents.firstObject.bundleIdentifier == com.apple.camera` 作为保守 gate；内部 scene matching C 函数仅记录为后续音量键拦截层设计依据，当前不硬链接。

1.9.13 资源中 `libactivator.phone.answer-call` 和 `libactivator.phone.disconnect-call` 的 selector metadata 都是 `answerCall`。这会让两个不同动作在资源层共享同一 selector，当前已将 `disconnect-call` 规范化为 `disconnectCall`，并让 telephony listener 继续以 selector metadata gate 区分动作。`answer-call` 参考 `TRAppIntentXpcServiceConnection.mm`，通过项目内私有 `CTCall.h` 副本和 `CoreTelephony.framework` 链接枚举当前 calls，查找 `kCTCallStatusIncomingCall` 并调用 `CTCallAnswer`。`disconnect-call` 使用同一参考中的“terminate any calls”路径，调用 `CTCallListDisconnectAll` 来覆盖活动通话和来电拒接场景。

`libactivator.phone.answer-call` 出现首个来电可接、后续来电不可接但仍可挂断后，重新对比了 `TRAppIntentXpcServiceConnection.mm` 与 `TRAppIntentXpcServiceTelephonyCenter.mm`。参考项目的 answer 方法本身同样在 main queue 中调用 `CTGetCurrentCallCount`、`CTCopyCurrentCalls`、逐个检查 `CTCallGetStatus(call) == kCTCallStatusIncomingCall`，然后调用 `CTCallAnswer(call)`；但同一服务还存在一个持久的 `CTTelephonyCenter` observer，订阅 `kCTCallStatusChangeNotification` 和 `kCTCallIdentificationChangeNotification`。由于 answer 依赖当前 incoming `CTCallRef`，而 disconnect 使用全局 `CTCallListDisconnectAll()`，漏掉 observer 会导致“后续 answer 依赖的 current calls / status 没有刷新，但 disconnect 仍可用”的表现。当前 `LATTelephonyActionListener` 已补齐 `LATTelephonyCallStateObserver`，在 listener 生命周期内持续接收 CoreTelephony call 状态变化，并保留 call count、copied call object count、call status/type/address 与 answer request 诊断日志。

## Back actions

旧 master 源码没有 `libactivator.system.local-back`，但 1.9.13 的 `ActivatorSpringBoard` 二进制中 `_LASimpleListener` 同时实现了 `-goBackWithActivator:event:` 和 `-localBack`。资源层 `libactivator.system.back` 使用 selector `goBackWithActivator:event:`，`libactivator.system.local-back` 使用 selector `localBack`。IDA 中 `goBackWithActivator:event:` 的 IMP 为 `0x8648`，`localBack` 的 IMP 为 `0x8704`；`goBackWithActivator:event:` 先设置递归 guard，然后读取 `LASharedActivator.currentEventMode`。如果当前 mode 是 `LAEventModeApplication`，它设置 back 状态并 `notify_post("libactivator.system.back")`，随后返回 handled；如果当前 event name 是 `libactivator.menu.press.single`，它返回未处理，避免 Home/Menu 单击触发 Back 后递归再按 Home；其余非 application mode 场景 fallback 调用 `homeButton`。`localBack` 则设置 local-back 状态并 post 同一个 Darwin notification。真正的 UIKit back 行为在被注入到 App 进程的 `/usr/lib/libactivator.dylib` 中执行：1.9.13 的 `Activator.plist` 使用 `com.apple.UIKit` filter，App 端注册 `libactivator.system.back` Darwin notification，收到后从 `UIApp.keyWindow.rootViewController` 开始递归处理 presented / child view controllers，必要时调用 `dismissViewControllerAnimated:completion:`，最后在 `UINavigationController` 且 `viewControllers.count >= 2` 时调用 `popViewControllerAnimated:YES`。当前项目不恢复旧 `com.apple.UIKit` 注入，但 `system.back` 复刻可见分支：application mode 走现代 `local-back`，非 application mode 发 Home HID，menu single 触发时返回未处理。

现代 `libactivator.system.local-back` 改用 Voice Control 的“返回”实现。对 `/Users/82flex/Desktop/dyld/com.apple.dyld_16.7` 中 dyld shared cache 先执行 DSC image 加载 `/System/Library/PrivateFrameworks/SpeechRecognitionCommandAndControl.framework/SpeechRecognitionCommandAndControl`，再逆向 `-[CACSpokenCommand goBack]`：实现先调用 `CACSpokenCommandManager labeledElementsFromScreenWithTrait:`，trait 常量经加载 region 后读出为 `0x08000000`，命中后取第一个 labeled element 的 `element` 并调用 `press`；若找不到，则用 `CACLocaleUtilities localizedUIStringForKey:@"SafariBackButtonLabel"` 查找 Safari 返回按钮标题并同样 `press`；再失败时调用 `screenElementsForEscape`，遍历候选 `AXElement` 并调用分类方法 `cacPerformExcapeAction`，其实现是 `performAction:2013`。`AccessibilityUtilities.framework` 中 `-[AXElement performAction:]` 对 `2013` 先向底层 `uiElement` 执行 `performAXAction:2013`，失败时尝试 `remoteParent`。`CACSpokenCommandManager labeledElementsFromScreenWithTitle:`、`labeledElementsFromScreenWithTrait:` 和 `labeledElementsFromScreen` 都只读取 `_labeledScreenElementsCollection`；`forceElementFetchWithReason:` 会调度 `_fetchElements`，但真机 crash report `SpringBoard-2026-06-16-160327.ips` / `160343.ips` 显示独立调用该路径会在 `-[CACSpokenCommandManager _fetchElements]` 中的 `dispatch_async` 崩溃，原因是 Voice Control 服务生命周期未初始化内部 fetch queue。当前 runtime 因此不调用 `CACSpokenCommandManager`，而是直接用 `AXElement systemApplication.currentApplications.visibleElements` 作为候选元素来源，并按原 `goBack` 的三段顺序执行：back button trait `press`、Safari back title `press`、`performAction:2013` escape。Voice Control 关闭时，真机日志显示 AXRuntime 会因 “app ax and automation are off” 拒绝当前元素查询；hook `_AXSApplicationAccessibilityEnabled()` 与临时置位 `gAXAccessibilityTurnedOnOnce` 均未能让该 notification `1021` 门控放行。当前实现改为在动作前通过 `LAActivator` 私有 application accessibility 接口请求 SpringBoard 侧调用 `_AXSApplicationAccessibilityEnabled` / `_AXSApplicationAccessibilitySetEnabled`，发现 app ax 关闭时真实打开它；该状态不会由 `local-back` 自动关闭，包卸载前通过隐藏 CLI `activator prerm` best-effort 关闭。

`libactivator.keyboard.dictation` 的旧 `ActivatorSpringBoard` 入口只设置状态并 `notify_post("libactivator.keyboard.dictation")`；真实动作在旧 `/usr/lib/libactivator.dylib` 的 `com.apple.UIKit` 注入端执行，收到 Darwin notification 后调用前台 App 内的 `UIDictationController` / `UIKeyboardImpl` 路径。当前项目不恢复用户 App 注入。Consumer page `0x0C` / usage `0xCF` 的 VoiceCommand HID 能被 BackBoard 记录为 `VoiceCommand page:0xC usage:0xCF` down/up，但未触发实际听写 UI；现代实现因此复用 `local-back` 的 AX 元素 helper，在 SpringBoard 主队列打开 application accessibility 后枚举当前应用 `visibleElements`。真机 probe 显示启动听写键在键盘 keyplane 中使用 `0:` 前缀 identifier，中文环境为 `0:30`，但该值更像布局位置 token，不适合作为唯一语义；听写中停止入口的用户可见标题是“键盘”而不是“停止听写”。当前 runtime 因此实现为 toggle：先用多语言“键盘/Keyboard/…”标题匹配停止入口，失败后再用 `0:` keyplane identifier 前缀加多语言“听写/Dictation/…”标题匹配启动入口。
