# libactivator 重写规范

本文件是关于重写 libactivator 的工作协议。它是 起初故意保持简洁；一旦我们达成一致，相关决策应移至此处 已足够稳定，足以指导实施。

## 参考基准

- 公共 API 基准：`references/headers`，源自 `origin/headers` (`bfac8ee70e8ad6560305dc7f0fa586c1b5696ef1`, 公开版 1.9.0)。
- 旧版实现参考：`references/master`，源自 `origin/master` (`b245f923bb683a902e932c9307286bcaa9a26cd3`, 公开版本 1.6.2-1)。
- 旧版实现仅供行为参考。请勿复制旧版 除非我们明确批准它们在 iOS 15 及以上版本中使用，否则请勿采用这些实现模式。
- 请假设旧版实现中使用的所有 iOS SPI 均已失效。
- 假设旧版实现所使用的每个 iOS 公共 API 都必须进行映射 在正式采用之前，先将其适配为现代的 iOS 16.5 SDK 版本。
- 请勿使用已弃用的 API。
- 如果 SPI 无效，且没有可靠的现代 iOS 反编译工具 请参考相关资料，不要凭空编造实现方案，也不要在网上搜索猜测性的答案。 先留个占位符，然后立即咨询项目负责人。

## 项目目标

- 请将此次重写视为该项目在新的维护框架下的延续。 假设原作者不会回来维护这个遗留项目。
- 将新项目版本号设为 2.x。
- 保留最终的公共 API，确保其与源代码兼容，并对其进行扩展。
- 支持 iOS 15.0 及更高版本。
- 支持带root权限、无root权限和隐藏root权限的越狱布局。
- 使用 Theos 进行构建，采用 `$THEOS` 及其 iOS 16.5 SDK。
- 针对 `arm64` 和 `arm64e` 进行构建。

## 兼容性规则

- 公共类名、协议名、选择器、常量以及预期 `references/headers` 中的语义是兼容性契约。
- 最终的 1.9 公共 API 设计方案具有权威性。旧版 `master` 该实现仅供参考，不得覆盖公共 API 合同。
- API 扩展必须是增量式的，除非我们有意创建一个已记录的 兼容性中断。
- 在仍有必要的情况下，保留向后兼容的模型。当一个旧版 如果某种行为属于 bug、不安全的设计或过时的负担，请记录下来并标记为 将兼容性接口标记为已弃用，而非保留旧行为 盲目地。
- 新行为应优先采用优雅的无操作（no-op）或显式错误报告，而非 当缺少监听器、事件、私有 API 或 SpringBoard 功能时，程序会崩溃。
- 即使实现方式发生变化，也要保持旧版事件和监听器名称的稳定性， 完全崭新的。

## 建筑规范

- 保持公共客户端库的体积小巧且稳定。
- 将 SpringBoard 专用的私有 API 使用置于 SpringBoard 运行时之后 层。
- 在 SpringBoard 内部对 UIKit、SpringBoard 和 FrontBoard 的私有 API 调用必须 除非已证实某个特定的 API 是线程安全的，否则应在主队列上运行。
- 重写的 libactivator 绝不能注入到用户应用程序中。
- 只有当包标识符为 已明确知晓，且以 `com.apple.` 开头。
- 请勿使用 `com.apple.UIKit` 注入过滤器，因为它会注入到所有 应用程序，并带来广泛的兼容性风险。
- 在 Apple 应用中注入内容时，必须使用明确的按包过滤器，并且必须有正当理由 由需要该功能的功能调用。请勿添加通配符 Apple 应用注入。
- 预计在现代 iOS 系统上将支持应用内状态栏的触控操作 无需应用注入；请查阅具体实现情况，当 该功能已开发完成。
- 如果未来某项功能确实需要注入用户应用程序，请将其实现为一个 将该组件作为独立的可选组件，置于 libactivator 之外。
- 请将这些职责分开：
- 公共 API 门面。
- IPC 客户端和服务器协议。
- 事件注册表和元数据。
- 监听器注册表和元数据。
- 任务、个人资料和黑名单的存储。
- SpringBoard 事件获取适配器。
- 内置的操作/监听器实现。
- 设置界面。
- 越狱路径/布局抽象。
- 事件语义和事件获取绝不能属于同一个模块。一个手势 名称是固定的；检测该名称的钩子或识别器可能会因 iOS 版本而异 版本或环境。
- 先设计核心，并确保其稳固可靠。内置事件、监听器以及 随后应逐一逐步实施这些措施。
- 现代的前台应用查询、锁屏状态和主屏幕状态 已知有项目业主的推荐人。在 实现该运行时层。
- SpringBoard 运行时是 Activator 运行时的权威所有者 状态。事件注册表、监听器注册表、分配、配置文件、 黑名单状态、元数据分发和事件传递必须在此处汇聚 一旦IPC实现后。
- 非 SpringBoard 客户端应将 `LAActivator` 视为公共 API 的门面。 由运行时支持的调用必须通过 IPC 转发至 SpringBoard，或者使用一个 明确的、不会导致程序崩溃的备用方案。
- 在以下情况下，`libactivator.dylib` 内部的运行时模型行为是可以接受的： 用于纯逻辑验证的核心模型阶段。请勿将每个进程 将客户端中的本地注册表作为最终的运行时设计。
- 用于注册 Objective-C 对象的 API，例如监听器和事件数据源 注册和 SpringBoard 运行时是 SpringBoard 运行时的概念。非 SpringBoard 行为必须 必须明确指定，且不得在用户不知情的情况下创建一个仅限客户端的隔离运行时。
- 在 SpringBoard 外部发起的公共对象注册请求应被拒绝 并具备详细的运行时日志记录功能。它们不得显示用户界面，也不得创建本地客户端 注册项，且不得将其视为缺失的跨进程对象 注册。
- 返回对象的监听器查找使用外部的私有远程代理 当权威的 SpringBoard 注册表报告称一个 监听器已存在。此代理是兼容性行为，而非跨进程行为 对象注册，而非公共 API 扩展。
- 本地化是核心兼容性层的一部分。公共本地化 方法应首先查询 Activator 支持包，使用 event/listener 将元数据作为备用方案，仅在此之后才回退到稳定的字面量 字符串。
- 事件和监听器的资源元数据位于 Activator 支持下 目录，且必须在运行时通过 `jbroot(...)` 进行解析。请勿使用 实现代码中直接使用的 `/Library/Activator` 路径。

## 开发阶段

这些阶段描述的是工程依赖关系顺序，而非繁琐的里程碑。

- 建立现代 Theos 基础：目标、安装路径、公共头文件 分阶段处理、越狱路径抽象、格式化以及空构建验证。
- 实现公共 API 和核心模型：与 1.9 兼容的类、常量、 立面行为、事件模型、监听器模型、赋值、配置文件以及 黑名单逻辑。
- 实现存储和元数据：经过验证的模式、原子性持久化， 序列化行为、本地化、图标、配置钩子、移除 钩子、事件元数据和监听器元数据。
- 使用 `CPDistributedMessagingCenter` 实现请求/响应处理， 错误处理、通知和有效载荷验证。
- 实现 SpringBoard 运行时：服务器引导、运行时状态、 前台应用状态、锁屏/主屏幕状态、监听器注册、事件分发、 诊断以及基于Frida的验证工作流。
- 按事件家族分阶段实现事件采集。每个事件必须 在注册前进行一次现代 iOS 能力评估。
- 分阶段实现内置监听器/操作。每个监听器/操作必须 在注册前进行一次现代 iOS 能力评估。
- 实现设置 UI 库及其宿主文件：`libactivatorsettings.dylib`，该 PreferenceBundle 主机、Activator.app 主机以及第三方主机的加载。
- 硬件设计集成与封装：片上验证检查清单、调试 traces、rootful/rootless/roothide 包检查以及发布文档。

## 构建规则

- 请使用现代的 Theos 项目结构，而非旧版的 `framework` 子模块。
- 为新代码使用简洁的组件名称：独立应用使用 `LAApp` Activator 应用，用于设置界面代码的 `LAS` 或 `LASettings`，`LAP` 或 “设置”偏好设置面板中的 `LAPreferences`，仅限 `ActivatorTweak` 主要调整目标和主配置文件，以及 `LAT` 或 `LATweak` 用于 额外的调整——本地类、文件和私有类型。
- 将部署目标设置为 iOS 15.0。
- 为 `arm64 arm64e` 构建所有生产二进制文件。
- 通过一个扁平化的兼容性入口点公开公共头文件，并 框架风格的标准路径，符合 Theos 的规范，例如 `substrate.h`：应包含 `/usr/include/libactivator.h` `<Activator/Activator.h>`，而标准的公共头文件位于 `/usr/include/Activator/` 和 `Activator.framework/Headers/`。
- 请勿在 `/usr/include/libactivator/` 目录下安装公共头文件。
- 请将包元数据保存在根目录 `layout/` 下的最终包路径处。
- 请将每个调整程序的过滤器 plist 文件保存在该调整程序子项目的根目录下，以便 Theos 能够 通过常规的 `tweak.mk` 流程进行构建。请勿放置 tweak 过滤器 plist 文件 在仓库根目录下。
- 请勿在此项目中使用 Logos 语法。Tweak 目标应使用常规 Objective-C 或 Objective-C++ 源文件，且不应使用 `.x` 或 `.xm` 源扩展。
- 使用根聚合 Makefile 来协调二进制子项目。请勿混用 将无关目标的所有权移至根包/暂存层。
- 请勿在项目的 Makefile 中定义 `$THEOS`。调用方必须通过 环境变量或命令行。
- 请勿覆盖 Theos 的内部路径变量或编译器缓存路径 项目 Makefile，包括 `THEOS_LIBRARY_PATH`、`THEOS_PACKAGE_DIR` 和 CLANG_MODULE_CACHE 的路径。
- 请将目标所属的源文件保存在其所属的子项目中。共享 实现文件可能位于 `subprojects/common` 目录下。
- 避免在源代码中隐含地假设 SDK 版本。对私有符号进行访问控制，并 动态启用可选的运行时功能。
- 请勿将生成的构建产物提交到源代码控制系统。
- 设备集成测试必须在 `LA_TESTING` 环境后进行隔离。常规构建 不得编译仅用于测试的源文件、测试IPC消息、测试设备 自动化，或测试持久化路径。
- `scripts/run-tests.sh` 是当前设备集成测试的入口点。它 要求调用者先准备好所需的越狱环境，然后它 运行 `gmake do LA_TESTING=1`，并通过 安全外壳协议
- 设备测试必须比较运行器执行前后 SpringBoard 的 PID。 即使测试运行器已退出，也应将 PID 变更视为 SpringBoard 重启 成功地。

## 越狱布局规则

- 请勿使用诸如 `/Library`、`/usr/lib` 或 通过功能代码访问 `/var/mobile`。
- 通过一个路径抽象层，统一管理安装路径和运行时查找路径。
- 路径决策必须分别考虑包含根节点、不包含根节点和隐藏根节点的情况。
- Theos 和 theos-roothide 处理了大部分包布局的差异。重写 应重点确保运行时路径的正确识别。
- 将 `$THEOS/vendor/include/roothide.h` 作为 roothide 的主要参考文件 运行时路径处理。
- 应将包布局和运行时发现规则记录在 路径抽象一旦实现。

## IPC规则

- 将旧版 `CFMessagePort` 协议视为行为参考，而非 默认设计。
- 使用 `AppSupport` 框架中的 `CPDistributedMessagingCenter` 作为进程间通信（IPC） 层。将其视为该功能的集成 XPC 客户端/服务器边界 项目；不要在其周围构建额外的 Direct-XPC 层。
- `CPDistributedMessagingCenter` 不会绕过沙箱限制。如果一个 沙箱化系统服务后续需要跨进程通信，请添加 `libSandy` 仅适用于该特定桥接。请勿在 没有具体沙箱跨界要求的阶段。
- 新的IPC层必须定义请求/响应格式、通知以及故障处理 行为和有效载荷验证。
- 请勿在 `CPDistributedMessagingCenter`。客户端和 SpringBoard 服务器随附 一起，且安装后需要重启 SpringBoard。
- IPC 使用 `libactivator.springboard` 作为 `CPDistributedMessagingCenter` 名称。非 SpringBoard 的 `LAActivator` 客户端可以查询和修改状态/配置 通过此通道，事件分发调用可能会被转发至 SpringBoard 权威运行时。
- State/config IPC 有效载荷必须是符合属性列表规范的字典。事件是 由 `EventName` 和 `EventMode` 表示；监听器名称、配置文件名称以及 显示标识符是普通字符串或字符串数组。
- 事件分发的 IPC 负载必须保持属性列表安全。事件是 由 `EventName`、`EventMode`、`EventHandled` 以及可选的 `UserInfo`；不符合属性列表安全规范的 `UserInfo` 值在跨 流程边界。
- 状态/配置 IPC 响应使用 `OK` 布尔值和可选的 `Value`。事件 分发回复时使用 `OK` 和 `EventHandled`。当服务器不可用时 或者有效载荷无效，客户端将返回该情况下的现有安全默认值 必须是公共选择器，且不得写入本地持久化运行时状态。
- 监听器对象的注册和事件数据源对象的注册仍然存在 在 SpringBoard 中具有权威性。跨进程对象注册不属于 当前的 IPC 切片；如果稍后实现，它必须通过 SpringBoard 进行代理 而不是创建孤立的客户端本地运行时状态。
- IPC有效载荷在使用前必须经过验证。
- 跨越进程边界的公共 API 调用应具有可预测的主进程 线程行为。
- 公共通知是进程内 `NSNotification` 的名称。跨进程 状态变更应通过IPC进行传播，然后由 每个客户端进程。
- 仅在 `LA_TESTING` 环境下允许测试 IPC。它绝不能出现在 普通包的构建或公开头文件。

## 数据规则

- 定义作业、配置文件、黑名单条目、事件元数据的模式， 以及收听者的元数据。
- 无法直接从旧版 Activator 安装包升级到此重写版本 一种预期用例。请勿在设计中加入自动迁移旧版偏好设置的功能 核心。
- 如果以后需要导入旧版首选项，请将其实现为显式 独立的导入工具，而非核心启动行为。
- 新持久化数据的写入应具有原子性，需经过模式验证，并且应显式指定 关于所有权和权限。
- 应优先采用结构化序列化，而非临时性的字符串解析。
- 运行时首选项必须存储在 `jbroot(@"/var/mobile/Library/Preferences/libactivator.plist")`。无需越狱且 roothide 的构建过程不得向实际的 `/var/mobile` 路径写入数据。
- 测试构建必须使用隔离的运行时首选项路径 `jbroot(@"/var/mobile/Library/Preferences/libactivator.tests.plist")` 并且必须 切勿读取、写入、备份或恢复用户的实际运行时首选项 plist.
- v2 运行时首选项 plist 文件采用模式版本 `1`，其中包含以下顶级 键：`SchemaVersion`、`CurrentProfileName`、`Profiles`、 `BlacklistedDisplayIdentifiers` 和 `SeenListenerNames`。
- “配置文件”下的每个条目都以配置文件名称为键，并包含一个 `Assignments` 字典。赋值操作以 `eventName -> modeKey -> listenerNames`，其中 nil 表示事件模式 用一个空字符串。
- 持久化的监听器名称数组和被列入黑名单的显示标识符数组必须 仅包含非空字符串，且已去除重复项并按顺序排列。
- 无效或无法读取的运行时首选项 plist 文件应被视为不存在。 请勿移动、删除、立即覆盖、迁移或重复使用旧缓存 plist 路径。

## 运行时规则

- 假设 SpringBoard 的私有 API 不稳定。请将每个私有选择器进行隔离 或者通过一个小型适配器进行类查找。
- `LAActivator` 是公共 API 的门面。私有运行时状态应位于 后端/持久化类型，而不是直接在门面层中。
- 只有 SpringBoard 的权威后端才能从该位置加载数据或将其保存至该位置 运行时首选项 plist。非 SpringBoard 客户端不得创建隔离的 在进行进程间通信之前，已存在持久状态。
- 建议采用功能检测，而非硬编码的系统版本分支。
- 所有事件处理程序在调用前都必须进行监听器兼容性检查。
- 监听器回调不应使事件获取层的阻塞时间超过 必要的。
- 处理状态、中止发送、预览发送、停用发送以及 多监听器赋值行为必须通过测试或显式方式进行验证 人工核验说明。
- 仅限 SpringBoard 的行为应通过设备端的轻量级测试进行验证 首先是诊断层和手动验证检查表，而不是通过繁琐的 自动线束。
- 可以通过 `frida -U SpringBoard` 命令在真实设备上运行 Frida 来检查 检查接口的可用性，添加临时钩子，并请项目负责人 执行用于验证挂钩行为的操作。

## 内置能力规则

- 在保留原有内置事件、监听器和操作名称时，应保持其名称的稳定性 公共兼容性接口的一部分。
- 每个内置事件、监听器和操作都必须独立进行评估，以 现代 iOS 功能，并在实施前已记录在案。
- 除非其现代 iOS 行为是 理解并落实。
- 如果某项旧有的内置功能在现代系统中已过时、不可用或不安全， iOS：记录原因，并保持其未注册状态或明确标记为不可用。

## UI 规则

- 保留原有的信息架构：模式、事件、监听器、搜索、 分配、配置文件、黑名单、菜单和配置控制器。
- 为 iOS 15 时代的 UIKit 重构用户界面。
- 请勿保留旧版广告界面、`UIWebView`、`UIAlertView` 或 `UIActionSheet` 模式。
- 设置界面应使用与第三方调用者相同的公共 API 接口 在可行的情况下使用。
- “真实设置”的 UI 逻辑必须位于一个独立的动态库中。
- `libactivator.dylib` 必须保留用于公共设置的兼容性适配层 来自 `LASettingsViewController.h` 的类，因为第三方越狱应用 可以动态链接 `libactivator.dylib`，并利用其中的类来呈现 设置界面。
- `LASettingsShims.m` 是一个狭义的兼容性例外：它可能包含 仅设置多个占位符类，因为此阶段提供的是空的 用于旧版公共 API 接口的兼容层。请勿将其视为实现 用于实际设置界面或未来运行时代码的模式。
- PreferenceBundle、Activator.app 以及第三方越狱应用是 设置 UI 库的托管服务。
- 在该合约就绪之前，请勿发布新的“设置”UI主机集成API 经过专门设计并获得批准。
- 请按照 `libxxx.dylib` 的命名规范为框架类动态库命名。
- 将 `libactivatorsettings.dylib` 作为“设置”界面动态库的文件名 除非实现细节要求使用更合适的名称。
- 将框架类动态库安装到 `$JBROOT/usr/lib` 目录下。
- 在以下位置显示相应的框架结构 `$JBROOT/Library/Frameworks`。
- 位于 `$JBROOT/Library/Frameworks/<Name>.framework` 中的框架二进制文件 应为指向 `../../../usr/lib/<library>.dylib` 的相对符号链接，其中 这是可能的，因为该符号链接本身位于 `.framework` 目录中。
- 主机必须动态加载“设置”用户界面动态库，并保持该库仅供主机使用 代码精简。

## 代码风格规范

- 除非 Theos/运行时边界有特殊要求，否则新编写的 Objective-C 代码应优先使用 ARC 否则。
- 默认情况下，请勿在新代码中使用手动内存管理。
- 请使用清晰的模块名称，并确保文件体积小且拥有明确的所有权。
- 新的实现代码应遵循每个源文件包含一个主要公共类的原则。 一个实现文件中允许包含多个类，但仅限于显式 已记录的兼容性适配层，或是完全属于私有的微型辅助类型 由该文件拥有。
- 请勿放置多个互不相关的运行时、模型、持久化、进程间通信（IPC）或用户界面 将实现类放在同一个源文件中。
- 除代码所需兼容性全局变量外，请避免使用全局可变状态 公共 API，例如 `LASharedActivator`。
- 请保持注释简洁且有价值：说明私有 API 的选择及兼容性 怪癖和难以察觉的同步问题。
